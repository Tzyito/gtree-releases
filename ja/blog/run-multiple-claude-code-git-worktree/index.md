# Claude Code を複数並列で動かす方法 — git worktree 入門

> 複数の Claude Code を同じリポジトリで並列に動かすなら、セッションごとに git worktree を用意するのが確実です。実際のコマンド、つまずきやすい点、手間を省く方法をまとめました。

Published: 2026-10-10 · DobbyLab · https://gtree.dobbylab.com/ja/blog/run-multiple-claude-code-git-worktree/

同じリポジトリで Claude Code を複数並列に動かすなら、**セッションごとに git worktree を 1 つずつ用意する**のが確実です。worktree は同じ `.git` の履歴を共有しながら、別のブランチをチェックアウトした独立した作業ディレクトリです。`git worktree add ../myapp-fix-login -b fix-login` で作成し、その中で `claude` を起動する。これをタスクの数だけ繰り返せば、各 AI は互いのファイルを上書きすることなく、並行して編集・ビルド・テストを進められます。

考え方はこれだけです。本記事では、実際に入力するコマンド、最初の 1 週間でつまずきやすい点、そして gtree がその繰り返し作業をどう肩代わりするかを説明します。

## 同じフォルダで Claude Code を 2 つ開くだけではだめなのですか?

開くこと自体はできますし、質問するだけなら問題ありません。しかし両方のセッションがファイルを編集し始めると、隔離のない 1 つの作業ディレクトリを共有することになります。

- セッション A が `auth.ts` を書き換えた直後に、古い内容を読んだままのセッション B がもう一度書き換える。
- A の作業途中の変更でビルドが壊れ、B が実行するテストは原因不明のまま失敗し続ける。
- コミットするときには、2 つのタスクの変更が 1 つの diff に混ざってしまう。

ブランチだけでは解決できません。1 つのフォルダでチェックアウトできるブランチは同時に 1 つだけだからです。worktree なら、それぞれが専用のブランチ・未コミットの変更・ビルド成果物を持つ実ディレクトリになり、コミットやブランチ、リモートはすべて共有されます。

## Claude Code 用に git worktree をセットアップするには?

メインのチェックアウトの中で次を実行します。

```bash
# 1. リポジトリの隣に worktree を作成し、新しいブランチを切る
git worktree add ../myapp-fix-login -b fix-login

# 2. その中で Claude Code を起動
cd ../myapp-fix-login
claude
```

別のターミナルを開き、次のタスクでも同じことをします。

```bash
git worktree add ../myapp-search -b search-box
cd ../myapp-search
claude
```

よく使うコマンドは次のとおりです。

| コマンド | 内容 |
|---|---|
| `git worktree list` | すべての worktree のパス・コミット・ブランチを表示 |
| `git worktree add <パス> -b <新ブランチ>` | 新しいフォルダと新しいブランチを作成 |
| `git worktree add <パス> <既存ブランチ>` | 既存ブランチを新しいフォルダにチェックアウト |
| `git worktree remove <パス>` | worktree を削除(未コミットの変更があると拒否。`--force` で強制) |
| `git worktree prune` | 手動で消したフォルダの worktree 記録を掃除 |

タスクが終わったら、いつもどおりマージするか MR / PR を作成し、worktree を削除します。

## git worktree の注意点は?

ほとんどの手間は「新しい worktree には **git が追跡しているファイルしかない**」ことから来ます。

1. **依存関係は入っていません。** `node_modules`、`target/`、`.venv` などは `.gitignore` 対象なので、worktree ごとにインストールやビルドが必要です。ディスク容量と初回ビルドの時間を見込んでおきましょう。
2. **ローカル設定もありません。** `.env` など無視されている設定ファイルは、各 worktree にコピーするかシンボリックリンクを張ります。
3. **1 つのブランチは 1 つの worktree でしかチェックアウトできません。** 「すでにチェックアウトされている」と言われたら、新しいブランチを作ります。
4. **ポートが衝突します。** 2 つの worktree から dev サーバーを起動すると同じポートを取り合うので、片方を変えます。
5. **フォルダが溜まります。** `rm -rf` でフォルダを消しても git は覚えているので、`git worktree prune` を実行します。

どれも致命的ではありませんが、毎回意識しておく必要があります。

## 本当の課題は 5 つのターミナルを把握し続けること

環境が整うと、今度は別の問題が出てきます。5 つの Claude を 5 つのターミナルタブで動かすと、

- どれが**承認待ち**なのか、タブを全部めくるまでわかりません。
- どれが**作業を終えて**レビュー待ちなのかもわかりません。
- どの worktree がどのブランチで、`main` からどれだけ離れているのか、だんだん追えなくなります。
- 2 つの AI が別々の worktree で**同じファイルを編集**していても、マージするまで気づけません。

## gtree で複数の Claude Code を管理する

[gtree](https://gtree.dobbylab.com/ja/) は worktree を中心に設計された macOS ネイティブアプリです。リポジトリを開くと、コマンドラインで作ったものも含め、すべての worktree がサイドバーに並びます。

**worktree の作成:** 「ワークベンチ」で worktree カードを右クリックし「新規 worktree…」を選んでブランチ名を入力します。gtree が `git worktree add` を実行し、リポジトリの隣にブランチ名のフォルダを作ります。削除も右クリックメニューから、確認つきで行えます。

**Claude の起動:** 「AI」ページには worktree ごとに内蔵ターミナルがあり、本物の `claude` コマンドが動いています。iTerm で使うのと同じ Claude Code なので、スラッシュコマンド、plan mode、承認プロンプト、MCP もそのまま使えます。必要なら同じ worktree で Claude のタブを複数開くこともできます。

**全セッションをひと目で:** サイドバーの各 worktree には状態アイコンが付きます。紫のアイコンが回転していれば Claude が作業中、赤いベルが点滅していればあなたの応答待ち、薄い紫のロボットなら開いているが待機中です。文字を読まなくても、赤いベルを探すだけで済みます。詳しくは次回の記事で紹介します。

**ブランチの状態:** ワークベンチの各カードに、ブランチ、未プッシュ / 未プルのコミット数、未コミットのファイル数が表示されます。コミット、プッシュ、プル、リベース、ブランチ切り替えはカードの右クリックメニューから実行でき、Mac 上の git を通すので SSH キーや hook もそのまま効きます。全ブランチの全体像は「変更 › コミット履歴」で確認でき、各ブランチにはチェックアウト先の worktree 名が付いています。

![コミット履歴のグラフ。fix/login、refactor/api-retry、feat/dark-mode などのブランチがそれぞれ色付きのレーンで描かれ、ラベルに worktree 名が並んでいる](/media/app/history-graph-ai-turns-ja-light.webp "「変更 › コミット履歴」。ブランチごとに 1 本のレーンがあり、ラベルでどの worktree にチェックアウトされているかがわかります")

**変更の確認:** 「変更 › 比較」は最初から「メインブランチ → 現在の worktree」で開くので、`git diff` を打たずにマージ前のレビューができます。

**衝突の事前通知:** 2 つの worktree が同じファイルを変更すると、マージを待たずにワークベンチ上部に警告が出ます。同じ worktree の 2 つのセッションでも、一方が直前に変更したファイルをもう一方が編集しようとすると、事前に知らせます。

### 手作業と gtree の比較

| | ターミナル + git | gtree |
|---|---|---|
| worktree の作成 | `git worktree add ../x -b x` | 右クリック →「新規 worktree…」 |
| Claude の起動 | 新しいタブで `cd` + `claude` | その worktree で AI ページを開く |
| 誰があなた待ち? | タブを全部確認 | サイドバーのベル + 通知 |
| ブランチの状態 | フォルダごとに `git status` / `git log` | worktree ごとのカード |
| 同じファイルの二重編集 | マージ時に発覚 | 両方が変更した時点で警告 |

## 5 セッションまで無理なく回せるワークフロー

1. メインフォルダは `main`(またはデフォルトブランチ)のままにし、AI には作業させない。
2. 1 タスク = 1 worktree = 1 ブランチ。ブランチ名はタスクに合わせる。
3. 各 Claude へのプロンプトで、担当するファイルや範囲を明確にする。
4. マージ前に `main` と比較してレビューし、終わったら worktree を削除する。
5. こまめにマージする。ブランチが長生きするほど差分は広がります。

## よくある質問

### Claude Code はいくつまで同時に動かせますか?

git 側に上限はありません。実際にはあなたの注意力、マシン性能(worktree ごとに依存関係やビルドが必要な場合があります)、Claude のプランの利用上限で決まります。3〜5 並列が扱いやすいという人が多いようです。

### worktree はディスクを大量に使いますか?

git の履歴は共有されるため、増えるのはチェックアウトされたファイルと、その中でインストール・ビルドしたものだけです。多くの場合 `node_modules` のような依存フォルダがいちばん大きくなります。

### gtree がないと worktree で Claude Code を使えませんか?

いいえ。上記はすべて git とターミナルだけで動きます。gtree が省くのは、worktree の作成、待っているセッション探し、編集の重なりの発見といった細かな作業です。

### gtree は Claude Code の代わりになりますか?

なりません。gtree は内蔵ターミナルで本物の `claude` を動かし、その状態を読み取るだけです。Claude Code の設定やサブスクリプションはそのままです。

gtree のローカル機能は無料で、登録も不要、gtree がコードをアップロードすることはありません。[こちらからダウンロード](https://gtree.dobbylab.com/ja/)して、作業中のリポジトリを開いてみてください。既存の worktree がサイドバーに並んでいるはずです。
